<Section id="loop" n="01" title="Open loop vs. closed loop" chip="Control loop">

In **open-loop** control the command ignores the result — simple and cheap, but
blind. A **closed loop** feeds the measured output back, comparing it to the
setpoint and acting on the *error*. PID lives inside the controller block below.

<Section id="code" n="06" title="Implementing PID in code" chip="Code">

The discrete form runs every loop iteration (here ~20 ms): compute the error,
accumulate the integral, take the derivative, and sum the weighted terms into a
motor command.

<CodeTabs>
<CodeTab label="Drive.java">

```java
public class Drive {
    double P = 0.6, I = 0.02, D = 4.0;
    double integral, previousError, setpoint = 0;
    Gyro gyro;
    DifferentialDrive robotDrive;

    public Drive(Gyro gyro) {
        this.gyro = gyro;
    }

    public void setSetpoint(double setpoint) {
        this.setpoint = setpoint;
    }

    public void pid() {
        double error = setpoint - gyro.getAngle();   // error = target - actual
        this.integral += error * 0.02;               // integral grows by error * dt (20 ms)
        double derivative = (error - previousError) / 0.02;
        double rcw = P * error + I * integral + D * derivative;
        previousError = error;
        robotDrive.arcadeDrive(0, rcw);
    }
}
```

</CodeTab>
<CodeTab label="Drive.cpp">


<Section id="sensors" n="07" title="Sensing for PID" chip="Sensing">

You've built a bare PID loop — it computes error, integrates, differentiates,
and outputs a motor command. But bare PID is only half the battle. To deploy it
on a real robot, you need two more pieces:

- **Sensing** — how to measure where the plant actually is (this section)
- **Actuation** — how to translate the PID output into motor commands (Section 08)

Put them together and you get **augmented PID**: feed-forward + feedback.

### The sensing pipeline

```
Environment → Sensors → Raw data → Perception → Low-dimensional state
```

For PID, we care about the final output: a single number or vector that the
controller can compare to the setpoint.

### Choosing the right sensor

| Sensor | Measures | Typical use on a robot |
|--------|----------|----------------------|
| **Incremental encoder** | Shaft rotation (ticks) | Motor speed, wheel distance |
| **Absolute encoder** | Angular position (0–360°) | Arm angle, swerve module angle |
| **IMU / Gyro** | Angular rate, heading | Drive trajectory, robot orientation |
| **Current sensor** | Motor current | Torque limiting, stall detection |
| **Limit switch** | Binary contact | Soft/hard stops, homing |

### The noise problem

Every encoder is noisy. A small amount of jitter is fine for P and I — they
**average** noise away. But the derivative term looks at the *rate of change*
of error, and sensor noise is high-frequency:

  u<sub>D</sub> = K<sub>d</sub> · d(noise)/dt → huge spikes

That's why in real code the derivative is **filtered** (low-pass). Many robot
frameworks (WPILib, etc.) apply a simple first-order filter:

```
filteredDerivative = α · newDeriv + (1 − α) · filteredDerivative
```

Where α is between 0 and 1 — smaller values give smoother output but add
latency. If your sensor is very noisy, reducing Kd is often easier than
fighting the filter.

### Sampling rate matters

PID runs every loop tick. If the period varies (e.g. network lag, slow sensors,
GC pauses in Java), the integral and derivative terms drift. Always pass the
actual loop period and clamp it:

```java
double dt = Math.min(actualDt, maxDt);   // guard against huge dt spikes
integrated += error * dt;
double deriv = (error - prevError) / dt;
```

A stable, known loop period (e.g. exactly 20 ms at 50 Hz) makes tuning far
more repeatable.

</Section>

<Section id="actuators" n="08" title="Actuation & feed-forward" chip="Actuation">

Now that you have a sensor reading and a PID output, you need to drive a real
actuator. Here's where things get interesting.

### Understanding actuators

A robot's actuator converts electrical energy into motion. Common types:

| Type | Pros | Cons | FRC example |
|------|------|------|-------------|
| **Brushed DC** | Cheap, simple | Brushes wear out, limited life | Talon SRX (brushed) |
| **Brushless DC** | Reliable, high power, low noise | More expensive, needs ESC | Falcon 500, NEO |
| **Stepper** | Precise open-loop, holding torque | Limited speed/torque at high RPM | 3D printer axes |
| **Servo** | Built-in control loop | Low power, not for drive | SG90, Dynamixel |

### Gearing

Motors spin fast with low torque. Gearing trades **speed for torque**:
higher gear ratio → more torque at the output, but slower max speed.

- **Spur gears**: simple, cheap, good ratio
- **Planetary gears**: compact, high ratio, efficient (NEO and CIM gearboxes)
- **Harmonic drives**: zero-backlash, very high ratio, expensive (robotic arms)

### Feed-forward control

Instead of waiting for error, calculate what the command *should be* using a
dynamic model. For a robotic arm:

  u<sub>ff</sub> = K<sub>g</sub>·cos(θ) + K<sub>v</sub>·ω + K<sub>a</sub>·α

Where:
- **K<sub>g</sub> (gravity FF)** holds the arm up at angle θ
- **K<sub>v</sub> (velocity FF)** anticipates viscous friction
- **K<sub>a</sub> (acceleration FF)** anticipates motor inertia

When feed-forward is good, the error is near zero — PID only handles
uncertainties, modeling errors, and disturbances. This is why real robots
achieve millimeter-level accuracy with relatively small PID gains.

### Pure PID vs Augmented PID

Pure PID works when you don't have a model. **Augmented PID** (feed-forward + PID)
is the real-world standard — feed-forward does the prediction, PID handles the
residual error. The full equation:

  u(t) = u<sub>ff</sub>(t) + K<sub>p</sub>e(t) + K<sub>i</sub>∫e + K<sub>d</sub>ė

### Fully actuated vs underactuated

- **Fully actuated**: # actuators ≥ # degrees of freedom. A mecanum drive (4 motors, 3 DOF),
  or the single-joint arm in our simulator (1 motor, 1 DOF).
- **Underactuated**: # actuators < # DOFs — a passive gripper, an acrobot, a double
  pendulum driven at one joint. You cannot command every DOF directly, so the
  unactuated ones have to be steered indirectly through the dynamics.

Gravity is a *force* acting on the arm, not a degree of freedom — the arm stays fully
actuated, and gravity feed-forward is exactly how you cancel that force before PID
ever sees it.

<Callout type="tip" title="Start with feed-forward, tune PID second">

In production robots, engineers tune K<sub>g</sub> and K<sub>v</sub> first
(usually by hand, measuring what voltage holds the arm at each angle), then
tweak K<sub>p</sub> for responsiveness and K<sub>d</sub> for smoothness.
K<sub>i</sub> is often zero unless there's a persistent disturbance like
sticky gears.

</Callout>

</Section>

<Section id="code2" n="09" title="Augmented PID in code" chip="Code">

The discrete form runs every loop iteration. Compute the feed-forward from your
motion model, compute the PID from the residual error, and sum them.

<CodeTabs>
<CodeTab label="Arm.java">

```java
public class ArmController {
    // Feed-forward constants (tune by hand — measure the voltage that holds
    // the arm still at a few known angles, then fit kG)
    static final double kG = 0.30;   // gravity compensation, at horizontal
    static final double kV = 0.0;    // velocity feed-forward
    static final double kA = 0.0;    // acceleration feed-forward

    // Feedback gains — tune after the feed-forward is close
    static final double kP = 0.02, kI = 0.0, kD = 0.001;

    private final PIDController pid = new PIDController(kP, kI, kD);
    private final TalonFX motor;
    private final Encoder encoder;

    public ArmController(TalonFX motor, Encoder encoder) {
        this.motor = motor;
        this.encoder = encoder;
        pid.setTolerance(0.5); // degrees
    }

    /** Call every loop tick (50 Hz). Angles are degrees from horizontal. */
    public void goToAngle(double setpointDeg) {
        double measuredDeg = encoder.getDistance();   // encoder configured in degrees

        // Feed-forward: gravity now, kV/kA once you have a motion profile
        double ff = kG * Math.cos(Math.toRadians(measuredDeg));

        // Feedback: PID on the residual error
        double pidOut = pid.calculate(measuredDeg, setpointDeg);

        // Combined command, clamped to the [-1, 1] duty-cycle range
        double output = MathUtil.clamp(ff + pidOut, -1.0, 1.0);
        motor.set(output);
    }
}
```

</CodeTab>
<CodeTab label="Arm.cpp (CTRE)">

```cpp
class ArmController {
    // Same gains as the Java version — kG at horizontal, kP/kD on the residual
    static constexpr double kG = 0.30;
    static constexpr double kP = 0.02, kI = 0.0, kD = 0.001;

    // Declaration order == construction order; keep the init list in this order
    frc::PIDController pid;
    ctre::phoenix6::hardware::TalonFX& motor;
    frc::Encoder& encoder;

public:
    ArmController(ctre::phoenix6::hardware::TalonFX& m, frc::Encoder& e)
        : pid(kP, kI, kD), motor(m), encoder(e) {
        pid.SetTolerance(0.5);  // degrees
    }

    // Call every loop tick (50 Hz). Everything below is in degrees.
    void Update(double setpointDeg) {
        double measuredDeg = encoder.GetDistance();  // encoder configured in degrees

        // Gravity feed-forward — cos() wants radians, so convert
        double ff = kG * std::cos(measuredDeg * M_PI / 180.0);

        // PID correction on the residual error
        double pidOut = pid.Calculate(measuredDeg, setpointDeg);

        // Combined, clamped to the [-1, 1] duty-cycle range
        motor.Set(std::clamp(ff + pidOut, -1.0, 1.0));
    }
};
```

<Section id="summary" n="12" title="Summary" chip="Summary">

You've walked through the full control loop — from open and closed loop, through
the three PID terms, tuning, sensing, actuation, feed-forward, and augmented PID.
Here's the mental model to carry forward:

- **Feed-forward** predicts what the command should be (from a model)
- **PID** corrects the residual error (from sensing)
- **Sensing** is only as good as your noise filtering
- **Gearing** trades speed for torque
- **Augmented PID** (u<sub>ff</sub> + u<sub>pid</sub>) is the real-world standard

When tuning on a real robot, start with feed-forward (K<sub>g</sub>, K<sub>v</sub>),
then add K<sub>p</sub> for responsiveness, K<sub>d</sub> for smoothness, and K<sub>i</sub>
only if you see persistent steady-state error.

</Section>
