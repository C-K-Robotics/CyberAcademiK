<Section id="code" n="06" title="用程式實作 PID" chip="程式">

離散形式會在每個迴圈週期（這裡約 20 毫秒）執行：計算誤差、累加積分、取微分，
再把加權後的三項加總成馬達指令。

<CodeTabs>
<CodeTab label="Drive.java">

```java
public class Drive {
    double P = 0.6, I = 0.02, D = 4.0;
    double integral, previousError, setpoint = 0;
    Gyro gyro;
    DifferentialDrive robotDrive;

    public Drive(Gyro gyro) {
        this.gyro = gyro;
    }

    public void setSetpoint(double setpoint) {
        this.setpoint = setpoint;
    }

    public void pid() {
        double error = setpoint - gyro.getAngle();   // error = target - actual
        this.integral += error * 0.02;               // integral grows by error * dt (20 ms)
        double derivative = (error - previousError) / 0.02;
        double rcw = P * error + I * integral + D * derivative;
        previousError = error;
        robotDrive.arcadeDrive(0, rcw);
    }
}
```

</CodeTab>

```cpp

};
```

<Section id="sensors" n="07" title="為 PID 做感測" chip="感測">

你已經寫出一個裸的 PID 迴路——它會計算誤差、積分、微分，然後輸出馬達指令。但裸
PID 只完成了一半。要把它部署到真實機器人上，還需要兩塊拼圖：

- **感測**——如何量測受控體實際的位置（本章節）
- **致動**——如何把 PID 輸出轉換成馬達指令（第 08 章）

把兩者合起來，就得到**增強型 PID**：前饋 + 回授。

### 感測流程

```
環境 → 感測器 → 原始資料 → 感知 → 低維度狀態
```

對 PID 而言，我們在意的是最終輸出：一個能讓控制器拿去和設定點比較的數值或向量。

### 選擇合適的感測器

| 感測器 | 量測對象 | 機器人上的典型用途 |
|--------|----------|----------------------|
| **增量式編碼器** | 軸的轉動量（脈衝數） | 馬達轉速、輪子行進距離 |
| **絕對式編碼器** | 角度位置（0–360°） | 手臂角度、swerve 模組角度 |
| **IMU／陀螺儀** | 角速度、航向 | 行進軌跡、機器人朝向 |
| **電流感測器** | 馬達電流 | 力矩限制、堵轉偵測 |
| **極限開關** | 二元接點 | 軟／硬限位、歸零 |

### 雜訊問題

每個編碼器都有雜訊。少量抖動對 P 和 I 沒什麼影響——它們會把雜訊**平均**掉。但
微分項看的是誤差的*變化率*，而感測器雜訊是高頻的：

  u<sub>D</sub> = K<sub>d</sub> · d(雜訊)/dt → 巨大的尖峰

這就是為什麼實務程式碼會對微分項做**濾波**（低通）。許多機器人框架（WPILib 等）
會套用一個簡單的一階濾波器：

```
filteredDerivative = α · newDeriv + (1 − α) · filteredDerivative
```

其中 α 介於 0 與 1 之間——數值越小輸出越平滑，但也帶來越多延遲。如果你的感測器
雜訊很大，調低 Kd 通常比跟濾波器拉鋸來得容易。

### 取樣率很重要

PID 每個迴圈週期都會執行一次。如果週期會變動（例如網路延遲、感測器太慢、Java
的 GC 暫停），積分與微分項就會漂移。永遠要把實際的迴圈週期傳進去，並加上上限：

```java
double dt = Math.min(actualDt, maxDt);   // guard against huge dt spikes
integrated += error * dt;
double deriv = (error - prevError) / dt;
```

一個穩定、已知的迴圈週期（例如 50 Hz 下剛好 20 毫秒）會讓調校結果好複製得多。

</Section>

<Section id="actuators" n="08" title="致動與前饋" chip="致動">

現在你有了感測器讀值與 PID 輸出，接下來要驅動真實的致動器。有趣的地方就在這裡。

### 認識致動器

機器人的致動器把電能轉換成運動。常見的類型：

| 類型 | 優點 | 缺點 | FRC 範例 |
|------|------|------|-------------|
| **有刷直流馬達** | 便宜、簡單 | 碳刷會磨耗，壽命有限 | Talon SRX（有刷） |
| **無刷直流馬達** | 可靠、高功率、噪音低 | 較貴，需要 ESC | Falcon 500、NEO |
| **步進馬達** | 開迴路即精準，保持力矩佳 | 高轉速下速度／力矩受限 | 3D 列印機軸 |
| **伺服馬達** | 內建控制迴路 | 功率低，不適合驅動底盤 | SG90、Dynamixel |

### 齒輪減速

馬達轉得快但力矩小。齒輪減速是用**速度換力矩**：齒輪比越高 → 輸出端力矩越大，
但最高轉速越慢。

- **正齒輪**：簡單、便宜、齒比不錯
- **行星齒輪**：體積小、齒比高、效率好（NEO 與 CIM 的齒輪箱）
- **諧波減速機**：零背隙、齒比極高、昂貴（機械手臂）

### 前饋控制

與其等誤差出現，不如用動力學模型直接算出指令*應該是多少*。以機械手臂為例：

  u<sub>ff</sub> = K<sub>g</sub>·cos(θ) + K<sub>v</sub>·ω + K<sub>a</sub>·α

其中：
- **K<sub>g</sub>（重力前饋）** 在角度 θ 撐住手臂
- **K<sub>v</sub>（速度前饋）** 預先補償黏滯摩擦
- **K<sub>a</sub>（加速度前饋）** 預先補償馬達慣量

前饋做得好時，誤差會接近零——PID 只需要處理不確定性、建模誤差與擾動。這就是為
什麼真實機器人可以用相對小的 PID 增益達到毫米級精度。

### 純 PID vs 增強型 PID

沒有模型時，純 PID 才是選項。**增強型 PID**（前饋 + PID）才是實務上的標準做法——
前饋負責預測，PID 負責殘餘誤差。完整式子：

  u(t) = u<sub>ff</sub>(t) + K<sub>p</sub>e(t) + K<sub>i</sub>∫e + K<sub>d</sub>ė

### 全驅動 vs 欠驅動

- **全驅動**：致動器數量 ≥ 自由度數量。例如麥輪底盤（4 顆馬達、3 個自由度），
  或我們模擬器裡的單關節手臂（1 顆馬達、1 個自由度）。
- **欠驅動**：致動器數量 < 自由度數量——被動夾爪、Acrobot、只在單一關節驅動的
  雙擺。你無法直接命令每一個自由度，未被驅動的那些只能透過動力學間接操控。

重力是作用在手臂上的*力*，不是一個自由度——手臂仍然是全驅動的，而重力前饋正是
你在 PID 看到它之前就把這個力抵消掉的方法。

<Callout type="tip" title="先調前饋，再調 PID">

在量產機器人上，工程師會先調 K<sub>g</sub> 與 K<sub>v</sub>（通常是手動量測在各個
角度撐住手臂所需的電壓），再調 K<sub>p</sub> 來拿到反應速度、調 K<sub>d</sub> 讓
動作平順。除非有像齒輪卡澀這種持續性的擾動，否則 K<sub>i</sub> 常常就是零。

</Callout>

</Section>

<Section id="code2" n="09" title="用程式實作增強型 PID" chip="程式">

離散形式會在每個迴圈週期執行。用你的運動模型算出前饋，用殘餘誤差算出 PID，
再把兩者相加。

<CodeTabs>
<CodeTab label="Arm.java">

```java
public class ArmController {
    // Feed-forward constants (tune by hand — measure the voltage that holds
    // the arm still at a few known angles, then fit kG)
    static final double kG = 0.30;   // gravity compensation, at horizontal
    static final double kV = 0.0;    // velocity feed-forward
    static final double kA = 0.0;    // acceleration feed-forward

    // Feedback gains — tune after the feed-forward is close
    static final double kP = 0.02, kI = 0.0, kD = 0.001;

    private final PIDController pid = new PIDController(kP, kI, kD);
    private final TalonFX motor;
    private final Encoder encoder;

    public ArmController(TalonFX motor, Encoder encoder) {
        this.motor = motor;
        this.encoder = encoder;
        pid.setTolerance(0.5); // degrees
    }

    /** Call every loop tick (50 Hz). Angles are degrees from horizontal. */
    public void goToAngle(double setpointDeg) {
        double measuredDeg = encoder.getDistance();   // encoder configured in degrees

        // Feed-forward: gravity now, kV/kA once you have a motion profile
        double ff = kG * Math.cos(Math.toRadians(measuredDeg));

        // Feedback: PID on the residual error
        double pidOut = pid.calculate(measuredDeg, setpointDeg);

        // Combined command, clamped to the [-1, 1] duty-cycle range
        double output = MathUtil.clamp(ff + pidOut, -1.0, 1.0);
        motor.set(output);
    }
}
```

</CodeTab>
<CodeTab label="Arm.cpp (CTRE)">

```cpp
class ArmController {
    // Same gains as the Java version — kG at horizontal, kP/kD on the residual
    static constexpr double kG = 0.30;
    static constexpr double kP = 0.02, kI = 0.0, kD = 0.001;

    // Declaration order == construction order; keep the init list in this order
    frc::PIDController pid;
    ctre::phoenix6::hardware::TalonFX& motor;
    frc::Encoder& encoder;

public:
    ArmController(ctre::phoenix6::hardware::TalonFX& m, frc::Encoder& e)
        : pid(kP, kI, kD), motor(m), encoder(e) {
        pid.SetTolerance(0.5);  // degrees
    }

    // Call every loop tick (50 Hz). Everything below is in degrees.
    void Update(double setpointDeg) {
        double measuredDeg = encoder.GetDistance();  // encoder configured in degrees

        // Gravity feed-forward — cos() wants radians, so convert
        double ff = kG * std::cos(measuredDeg * M_PI / 180.0);

        // PID correction on the residual error
        double pidOut = pid.Calculate(measuredDeg, setpointDeg);

        // Combined, clamped to the [-1, 1] duty-cycle range
        motor.Set(std::clamp(ff + pidOut, -1.0, 1.0));
    }
};
```

你已經走過了完整的控制迴路——從開迴路與閉迴路，到 PID 三項、調校、感測、致動、
前饋，以及增強型 PID。以下是值得帶著走的心智模型：

- **前饋**負責預測指令應該是多少（來自模型）
- **PID** 負責修正殘餘誤差（來自感測）
- **感測**的品質，取決於你的雜訊濾波做得好不好
- **齒輪減速**是用速度換力矩
- **增強型 PID**（u<sub>ff</sub> + u<sub>pid</sub>）才是實務上的標準做法

在真實機器人上調校時，先從前饋開始（K<sub>g</sub>、K<sub>v</sub>），接著加
K<sub>p</sub> 取得反應速度、加 K<sub>d</sub> 讓動作平順，只有在看到持續性的穩態
誤差時才動 K<sub>i</sub>。
